# 1. 概述

## 1.1 系统简介

restto（前身为 rustto）是一套分布式服务器数据备份系统，由三个独立子工程组成：部署在目标服务器上的 **Go 客户端**、提供业务与调度能力的 **Spring Boot 管理端后端**、以及供运维使用的 **Vue 管理前端**。三端之间通过自定义二进制帧协议（Netty TCP）与 RESTful 接口协同，完成节点注册、备份任务下发与执行、备份产物记录、工作流编排、客户端二进制分发等核心能力。

核心价值：把目标机上的备份能力拆成一个个独立的"工具（Tool）"，由管理端按名调度；新增一种备份只需在客户端实现一个 Tool 并注册一行代码，CLI 与常驻 daemon 无需其他改动即可识别并执行。客户端为纯 Go 静态编译（零第三方依赖），单个二进制可交叉编译到 6 种平台直接投放目标机。

## 1.2 三端架构

```
┌─────────────────┐    REST + JWT     ┌────────────────────┐
│   Vue 前端       │ ◄───────────────► │  Spring Boot 后端   │ ──► MySQL（Flyway V1–V3）
│ manager/client  │    /api（8080）    │  manager/server    │
└─────────────────┘                   │   ├ HTTP  :8080    │
                                      │   └ Netty TCP:9600 │
                                      └─────────┬──────────┘
                                                │ Netty TCP（自定义二进制帧协议）
                                                ▼
                                      ┌────────────────────┐
                                      │   Go 客户端         │ 部署在目标机，常驻
                                      │   processor/       │ CLI 工具调度 + daemon
                                      └────────────────────┘
```

说明：后端 HTTP（8080）与 Netty TCP（9600）运行在同一个 Spring Boot 进程内的两个监听端口；前端开发期由 Vite 代理、生产期由 Nginx 反向代理把 /api 请求转给后端 8080。

## 1.3 核心链路

① 前端登录获取 JWT，调用 RESTful 接口"新建节点"，后端生成并返回一次性节点 Token（UUID）。
② Go 客户端携带节点 Token，通过 Netty 长连接向后端发送 REGISTER 注册，之后周期性心跳保活。
③ 前端创建备份任务（指定模块 backup_file / backup_mysql、参数 JSON、cron 表达式），后端每分钟扫描，到点经 Netty 下发 TASK_COMMAND。
④ 客户端按 module 名调度到对应工具本地执行备份，回传 TASK_RESULT，后端落库为备份记录。
⑤ 上传新版本 Go 二进制后，经 Netty BINARY_PUSH 分片下发到目标节点，节点校验 sha256 后落盘。
⑥ 多个备份任务可编排为工作流（DAG）：按边条件（总是 / 成功 / 失败）驱动节点依次执行，支持画布设计与定时触发。

## 2.2 Go 客户端模块划分

| 目录 | package | 角色 |
| --- | --- | --- |
| client/restto | main | CLI 入口：daemon、tool list/schema/run、兼容旧命令、version |
| internal/common | common | Tool 契约：Tool 接口、ToolOutput（file_path/size/checksum）、ToolError 五类错误、RequireStr 参数校验 |
| internal/core/config | config | .env + 环境变量加载（已存在的环境变量优先） |
| internal/core/crypto | crypto | sha256（字节 / 64KB 缓冲流式文件哈希） |
| internal/core/logger | logger | 按日期滚动日志（文件 + 标准输出双写） |

| internal/backupmysql | backupmysql | 工具 backup_mysql：mysqldump 导出 + gzip |

## 2.5 Netty 通信协议（两端字节级对齐）

帧格式（大端）：

```
| magic 4B "RUST"(0x52555354) | length 4B BE（= 1 + payloadLen，含 type 字节） | type 1B | payload JSON |
```

| type | 消息 | 方向 | 说明 |
| --- | --- | --- | --- |
| 1 | REGISTER | C → S | 注册（node_name / node_token / version） |
| 2 | REGISTER_ACK | S → C | 注册结果（success / message / node_id） |
| 3 | HEARTBEAT | 双向 | 心跳（timestamp，Unix 秒） |
| 4 | TASK_COMMAND | S → C | 任务下发（task_id / module / args） |
| 5 | TASK_RESULT | C → S | 任务结果（task_id / status / 产物 / 错误） |
| 6 | BINARY_PUSH | S → C | 二进制分片（version / checksum / chunk / data） |
| 7 | BINARY_ACK | C → S | 二进制回执（version / success / error） |

注：魔数 "RUST" 为历史沿革，Go 客户端与 Java 服务端刻意保持一致以维持线上兼容（详见 10.5）。JSON 字段统一 snake_case。帧与字段详解见第 9 章。

# 3. 环境准备

## 3.1 工具链版本

| 工具 | 版本 | 说明 |
| --- | --- | --- |
| JDK | 1.8 | 后端编译运行 |
| Maven | 3.x | 后端构建 |
| Go | 1.24+ | 客户端编译（无任何第三方依赖） |
| Node.js | 18+ | 前端构建（Vite 8 要求） |
| MySQL | 8.0+ | 元数据与记录存储 |
| mysqldump | 与目标库匹配 | 目标机上使用 backup_mysql 工具时需要 |

开发环境为基于 WSL2 的 Ubuntu，使用 WSL 内的 node / go / java8 / maven。

## 3.2 数据库准备

后端依赖一个 MySQL 库（默认名 restto，utf8mb4）。表结构由 Flyway 在启动期自动创建（V1 初始化 + V2 RBAC + V3 工作流，共 17 张表），无需手工建表，只需建库：

```
mysql -uroot -p -e "CREATE DATABASE restto DEFAULT CHARSET utf8mb4;"
```

Flyway 配置了 baseline-on-migrate 与"checksum 不一致自动 repair 后重试"策略（FlywayConfig），对历史库升级友好；迁移脚本使用 CREATE TABLE IF NOT EXISTS + INSERT IGNORE 保证幂等。

# 4. 编译

## 4.1 编译后端（manager/server）

```
cd manager/server
mvn -DskipTests package        # 产物 target/restto-manager-0.1.0.jar
mvn spring-boot:run            # 开发期直接运行
```

## 4.2 编译前端（manager/client）

```
cd manager/client
npm install
npm run dev                    # 开发服务器 http://127.0.0.1:5173（--host 可局域网访问）
npm run build                  # 生产构建，产物 dist/
```

## 4.3 编译 Go 客户端（processor）

日常开发构建：

```
cd processor
go build ./client/restto           # 或 go run ./client/restto daemon
```

脚本化构建（processor/scripts/）：

| 脚本 | 作用 |
| --- | --- |
| build.sh | go build -ldflags "-s -w" 输出 bin/restto-client；--dev 关闭优化保留调试信息 |
| cross.sh | 交叉编译 6 目标，CGO_ENABLED=0 -trimpath，产物 dist-bin/<goos>-<goarch>/ |
| package.sh | 本地优化构建 + 收集 .env.example / README 打包 dist/restto-client-<版本>-<平台>.tar.gz |

默认交叉编译目标（归档名沿用 Rust target triple 风格，便于与历史版本对照）：

```
linux/amd64   → x86_64-unknown-linux-musl      linux/arm64 → aarch64-unknown-linux-musl
linux/386     → i686-unknown-linux-musl         windows/amd64 → x86_64-pc-windows-gnu
darwin/amd64  → x86_64-apple-darwin             darwin/arm64 → aarch64-apple-darwin
```

Docker 镜像：两阶段构建——alpine 按 TARGETARCH 从 dist/ 解出对应 musl 归档，FROM scratch 只装入单个静态二进制（ENTRYPOINT /usr/local/bin/restto-client）。镜像内不含 mysqldump，容器内运行 backup_mysql 需更换带客户端工具的基镜像。

# 5. 部署

## 5.1 部署拓扑与端口

| 组件 | 协议/端口 | 默认监听 | 说明 |
| --- | --- | --- | --- |
| 后端 HTTP | REST/JSON | 0.0.0.0:8080 | /api/**，JWT 鉴权 |
| 后端 Netty | 自定义 TCP 帧 | 0.0.0.0:9600 | 客户端注册/心跳/任务/二进制 |
| 前端（开发） | HTTP | 127.0.0.1:5173 | Vite 代理 /api → 8080 |
| 前端（生产） | 静态资源 | 由 Nginx 等托管 | history 路由需 fallback |
| MySQL | TCP | 3306 | 库名默认 restto |
| Go 客户端 | TCP 出站 | — | 主动连接后端 9600，目标机无需开放入站端口 |

## 5.2 部署后端

1) 准备库（见 3.2）；2) 在 jar 同目录放置 .env（由 DotenvLoader 在 main 最先加载，写入系统属性；已存在的环境变量优先）；3) 启动：

```
java -jar target/restto-manager-0.1.0.jar
```

.env 键清单（键见下表，完整默认值见 7.2）。关键默认值：数据库 restto / dev:12345678（可用 DB_USER / DB_PASSWORD 覆盖）；JWT 默认 720 分钟过期；Netty 9600；初始化管理员 admin / admin123。

注意：覆盖初始管理员口令的环境变量前缀为小写 restto_（restto_INIT_ADMIN_PASSWORD），这是改名遗留——Linux 环境变量区分大小写，导出大写 RESTTO_ 前缀不会生效（详见 10.5）。

启动自愈：DataInitializer 会在启动时自动修复 V1 种子中错误的 admin 密码哈希（V1 注释称 admin123，实际哈希对应 password），并确保 admin 用户与 admin 角色绑定存在。

## 5.3 部署前端

开发环境由 Vite 代理 /api → http://127.0.0.1:8080（需后端先启动）。生产环境：

- 将 dist/ 交由静态服务器（如 Nginx）托管；
- 因使用 HTML5 history 路由（createWebHistory），需配置 history fallback：未命中静态文件的路径一律回退到 index.html；
- 配置反向代理：将 /api/* 转发到后端 8080。

Nginx 参考片段：

```
server {
    listen 80;
    root /opt/restto/dist;
    location / { try_files $uri $uri/ /index.html; }
    location /api/ { proxy_pass http://127.0.0.1:8080; }
}
```

## 5.4 部署客户端到目标机

1) 在管理端"节点管理"新建节点，获得一次性 nodeToken；2) 把编译好的 restto-client 二进制（及 .env.example 改名为 .env）拷到目标机；3) 配置 .env（至少替换 NODE_TOKEN，按需改 MANAGER_HOST）；4) 以 daemon 常驻运行：

```
MANAGER_HOST=10.0.0.5 NODE_TOKEN=<节点Token> ./restto-client daemon
```

建议用 systemd / supervisord 托管，实现开机自启与异常重启；客户端内置断线 5 秒自动重连（固定间隔、无退避），心跳默认 15 秒。若使用 backup_mysql 工具，目标机需安装 mysqldump。备份产物与接收的二进制默认落在 DATA_DIR（默认 ./data），日志在 LOG_DIR（默认 ./logs）。

## 5.5 生产环境注意事项

- **立即修改默认管理员密码**：用环境变量 restto_INIT_ADMIN_PASSWORD 覆盖，或登录后重置。
- **务必用强随机值覆盖 JWT_SECRET**（至少 32 字节，HS256）。
- **收紧 CORS**：默认 allowedOriginPatterns("*") + allowCredentials(true) 全开，生产应限定为前端域名。
- **多实例限制**：PermissionCache（TTL 120s）、ConnectionRegistry（Netty 连接表）、调度器均为进程内状态，水平扩展需引入 Redis / 粘性路由，当前形态请单实例部署。
- **数据库迁移只增不删**：禁止删除/修改 db/migration 历史文件；新变更一律追加新版本脚本。
- **.env 为密钥文件**：不得提交版本库。注意当前仓库已追踪 manager/server/.env 且含真实数据库口令，建议尽快从版本库移除并轮换相关口令。
- 通信链路无 HTTPS/TLS（自定义 TCP + 默认 HTTP），生产请通过网络隔离 / 安全组保护 8080 与 9600 端口。
- 各端 .env 不得硬编码密钥；客户端 internal/core 不可修改（AGENT.MD 边界）。

# 6. 使用说明

## 6.1 登录

浏览器访问前端地址，默认账号 admin / admin123（首次登录后请立即修改）。登录成功后前端并行拉取用户信息（/auth/info：角色、权限码）与菜单树（/auth/menus），按菜单动态注册路由并注入按钮级权限指令 v-permission。admin 角色自动 bypass 所有权限校验。JWT 默认 12 小时过期，过期后任意接口返回 401，前端自动登出并跳转登录页。

## 6.2 仪表盘

登录后首页展示 4 张统计卡（节点总数 / 备份任务 / 备份记录 / 二进制版本，取分页 total 并行加载）与系统状态面板（Netty 9600、JWT+RBAC、AOP 审计说明）。

## 6.3 节点管理

"备份管理 / 节点管理"页：

- "新建节点"只需填写节点名；创建成功后弹窗一次性回显 nodeToken（**仅展示一次，请妥善保存**）。
- 把该 token 写入目标机客户端 .env 的 NODE_TOKEN，启动 daemon 即可注册上线。
- 列表展示节点状态（online/offline）、客户端版本、最近心跳时间；删除节点会同步清理其在线连接。
- 注意：节点 token 目前不支持轮换/重置，遗失只能删除节点重建；token 校验为明文字符串相等。

## 6.4 备份任务

"备份管理 / 任务管理"页可创建/编辑/删除/立即执行备份任务。任务字段：

| 字段 | 说明 |
| --- | --- |
| name | 任务名 |
| node_id | 目标节点（下拉选择） |
| module | 备份模块：backup_file / backup_mysql |
| params_json | 参数 JSON（与所选模块的参数 schema 对应，见 6.9） |
| cron_expr | 6 段 Spring 风格 cron（秒 分 时 日 月 周），如 0 30 2 * * * |
| enabled | 启用开关；调度器仅扫描 enabled=1 的任务 |

调度：后端每分钟扫描（fixedDelay 60s），用 Spring CronExpression 判定当前分钟到期即触发。"执行"按钮立即下发：节点在线则预置一条 pending 记录并下发 TASK_COMMAND，离线则直接返回未下发（不建 pending）。客户端执行完成后回传 TASK_RESULT，记录更新为 success/failed 并写入产物路径、大小、sha256、错误信息。

## 6.5 备份记录

"备份管理 / 记录管理"页可按任务过滤、分页查看历史备份记录，含状态（pending/success/failed）、产物路径、大小、起止时间、错误信息等。记录由任务下发时预置 pending、客户端回传时更新，也支持异常场景下的补录。

## 6.6 二进制版本管理与热下发

"备份管理 / 二进制管理"页：

- **上传**：选择文件、填写版本号后上传（multipart），后端流式计算并记录 sha256、大小、上传时间，文件存于 {BACKUP_DATA_DIR}/binaries/{version}/。
- **下发**：选择目标节点，后端将整包 base64 后按 512×1024 个 base64 字符/片（约 384 KiB 原始字节）切片，逐帧 BINARY_PUSH 下发。
- 客户端收齐分片后整体校验 sha256，通过则落盘为 DATA_DIR/restto-client-<version>.bin（权限 0755），并回传 BINARY_ACK。
- 注意：下发为单向流（不等 ACK、无分片重试）；客户端假设分片按顺序到达；落盘后**不会自动热替换/重启**，升级动作需外部介入（如配合 systemd 重启）。

## 6.7 工作流（v1.1 新增）

工作流把多个备份任务编排为有向无环图（DAG），按边条件驱动执行，解决"备份 A 成功后再备份 B、失败则转 C"一类联动需求。

**概念模型**：

- 节点（Node）= 引用一个已有的备份任务（node_key + task_id + 画布坐标）；
- 边（Edge）= source → target + 条件：always（总是）/ on_success（成功才走）/ on_failed（失败才走）；
- 执行（Execution）= 一次运行实例，状态 running / success / failed；触发方式 manual（页面"运行"）/ schedule（cron 到点）；
- 节点状态 waiting → running → success | failed | skipped。

**设计器**（"备份管理 / 工作流设计"，隐藏路由 /backup/workflow/design）：左侧任务面板点击添加节点 → 画布拖拽定位（20px 网格吸附）→ 从节点出口拖出连线 → 点击连线循环切换条件（总是=青 / 成功=绿 / 失败=红）→ 填写名称与 cron → 保存整图（nodes + edges）。

**引擎语义**（后端 WorkflowGraph + WorkflowExecutionService）：

- 保存时做 Kahn 拓扑校验，有环拒绝；
- 单线程引擎串行化状态迁移，IO（任务下发）由有界线程池执行；同一任务被多个在途节点引用时排队；
- 就绪判定：任一路径满足条件即可继续；上游被跳过（skipped）不会触发下游；任一节点 failed 即整次执行 failed；
- 节点离线/断连：该节点标 failed，防挂起；执行超时默认 30 分钟（restto.workflow.timeout-minutes），由每分钟一次的回收器处理；
- 后端重启后可从数据库重建执行上下文继续推进。

**执行历史**（"备份管理 / 执行历史"）：按工作流过滤查看历次执行，详情含每步节点的 nodeKey / 标签 / taskId / 状态 / 错误信息。

## 6.8 系统管理（RBAC）

权限模型：用户 → 角色 → 菜单/权限点。接口通过 @RequirePermission("code") 声明所需权限码（支持类级 + 方法级覆盖），前端按权限码控制按钮显隐（v-permission），路由按菜单树动态注册。admin 角色 bypass 全部校验（实时查库判定，不走缓存）。

默认角色：admin（超级管理员，拥有全部 16 项菜单与 49 个权限点）、viewer（只读访客：仪表盘 + 备份/工作流只读）。

| 子模块 | 主要能力 | 关键权限码示例 |
| --- | --- | --- |
| 用户管理 | 增删改查、分配角色、重置密码、启停 | system:user:create / assign-roles / reset-password |
| 角色管理 | 增删改查、分配菜单（树勾选）、分配权限（按模块分组） | system:role:assign-menus / assign-perms |

# 9. 通信协议参考

## 9.1 帧格式

```
| magic 4B "RUST"(0x52 0x55 0x53 0x54) | length 4B 大端（= 1 + payloadLen） | type 1B | payload JSON |
```

- length 字段 = type(1B) + payload 的总字节数，即 1 + payloadLen；单帧 payload 上限 256 MiB。
- 服务端用 LengthFieldBasedFrameDecoder(4 偏移跳过 magic) 处理粘包/半包；客户端按 9 字节头 + ReadFull 逐帧读取。
- 两端对坏帧的处理：magic 不符、未知 type、非法 JSON 均拒绝（服务端断开连接，客户端报错）；JSON 字段统一 snake_case，未知字段忽略（FAIL_ON_UNKNOWN_PROPERTIES=false）。

## 9.2 消息 JSON 字段

| 消息(type) | 字段 | 说明 |
| --- | --- | --- |
| REGISTER(1) | node_name / node_token / version | 客户端注册：节点名、Token、客户端版本 |
| REGISTER_ACK(2) | success / message / node_id | 注册结果；成功返回节点 ID，失败后服务端断连 |
| HEARTBEAT(3) | timestamp | Unix 秒；客户端周期上报，服务端收到后刷新心跳并原样回包 |
| TASK_COMMAND(4) | task_id / module / args | 任务下发；args 为 JSON 原样透传给工具 |
| TASK_RESULT(5) | task_id / status / file_path / size / checksum / error | 执行结果；后四项可空，status = success / failed |
| BINARY_PUSH(6) | version / checksum / chunk_index / total_chunks / data | data 为 base64 分片（512×1024 字符/片） |
| BINARY_ACK(7) | version / success / error | 接收回执；校验失败 error = checksum mismatch |

## 9.3 交互行为细则

**注册**：客户端连接后立即发送 REGISTER（不等 ACK 即开始心跳）；服务端按节点名查库并做 token 明文比对，通过则置节点 online、记录版本并回 ACK；失败回 ACK(false) 并主动断连——客户端会以 5 秒间隔无限重试（Token 错误将反复重连）。

**心跳**：客户端每 HEARTBEAT_INTERVAL_SECS（默认 15s）上报；服务端刷新 last_heartbeat_at 并回一帧 HEARTBEAT（客户端仅记 debug 日志不处理）。连接断开（channelInactive）时服务端立即将节点置 offline，并把该节点在途的工作流节点标为 failed。

**任务执行**：客户端收到 TASK_COMMAND 后按 module 经 tools.Lookup 调度（与 CLI tool run 同源），在独立 goroutine 执行（无并发上限）；结果经 128 帧缓冲的写队列回传，队列满时结果被丢弃并记日志。服务端收到 TASK_RESULT 后按"该任务最新一条 pending 记录"更新状态，无 pending 则补录。

**二进制下发**：服务端整文件读入内存 → 全量 base64 → 按固定字符数切片逐帧下发（不等 ACK、无重试）；客户端按到达顺序拼接分片（依赖顺序到达），收齐后整体 sha256 比对，通过则落盘 DATA_DIR/restto-client-<version>.bin（0755），不通过回 NACK 且不落盘。

**断线重连**：客户端任何会话错误后固定 5 秒重连（无退避、无上限）；服务端注册时同节点的新连接会顶替旧连接。

## 10.4 日志策略

客户端：标准库 log/slog（Text 格式），按日期滚动，文件名 client.log.YYYY-MM-DD，文件与标准输出双写；级别由 LOG_LEVEL 控制（默认 info）。

后端：Logback 滚动文件 logs/restto.log → restto.&lt;yyyy-MM-dd&gt;.log，保留 30 天、总量上限 2GB，同时输出控制台；com.restto 包默认 debug，org.flywaydb 为 info。

前端：无文件日志，依赖浏览器控制台与后端操作日志。

## 10.5 已知差异与注意事项

- **魔数仍为 "RUST"**：协议层刻意保留（Go 客户端与 Java 服务端同值对齐），属"故意不改"；个别代码注释仍写"Rust 客户端"，系注释未随迁移更新。
- **restto_INIT_ADMIN_* 小写前缀**：项目由 RUSTTO_ 更名时经大小写不敏感替换产生小写 restto_ 前缀；Linux 下导出大写 RESTTO_INIT_ADMIN_PASSWORD 不生效（回落默认 admin123），且这两个键未列入 .env 模板。
- **README 与实际不符处**：根 README 把后端目录写作 manager/web/（实际 manager/server/）；前端 README 写"Vite 5"（实际 Vite 8）；根 README 快速开始中的目录路径请以本说明书为准。
- **.env 已入版本库**：manager/server/.env 被 git 追踪且含真实数据库口令，与其"密钥文件不得提交"的约定冲突，建议移除并轮换口令。
- 代码中暂未实现：登出/刷新 Token、节点 token 轮换、HTTPS/TLS、备份产物与二进制的清理任务。
- 二进制下发不等 BINARY_ACK、无分片重试；客户端收包依赖分片顺序到达；落盘后不自动热替换，需外部介入重启。
- 备份管理四页（节点/任务/记录/二进制）的前端按钮未挂权限码（仅菜单级控制）；系统管理与工作流页已用 v-permission。
- 工作流列表页跳转使用 /workflow/design，与菜单种子注册的 /backup/workflow/design 不一致，首次跳转依赖前端兜底路由 + 守卫重导航机制生效（功能可用）。
- TokenInterceptor 豁免的 /api/auth/register 端点实际不存在；V1 种子密码哈希注释与实际不符（由 DataInitializer 启动自愈）；前端 package.json 中 lodash-es 为未使用依赖。
